# 5.8.0

QA's first behavioral run on an interaction ticket is the author's shared scenario run, and evidence has no size cap.

## Shared browser scenario run

From Super Awesome Games ticket VGD2A04892DB-38 (2026-11-13). QA rejected the same spike harness twice in a row:

- **First round.** A voice-cap violation the page's own checks missed.
- **Second round.** A brick path the record described from the plan, not from what happened.

Both defects were deterministic and present from the start. QA's ad hoc probes found one per round, and each round
cost a full rework cycle. The author had no way to observe behavior, so the record carried values reasoned from
source.

- **New tool `run_scenario_contract`.** It is also available per repository in delivery-scope QA. It runs
  `BrowserScenarios.PlaywrightScript` (CSweet.Agent.SDK 5.25.0) unchanged, as an ordinary source-bound behavioral
  script on the exact build `test_web_build` tested. This is the same contract and evaluator the author's receipt used.
  - Every check is judged from expected and observed values. A check whose observation cites no emitted event fails.
  - The run reports one assertion per acceptance criterion, so declared interaction criteria are cited.
- **The runner offers `attach('scenarios', value)`**, which keeps the full evaluation as `scenarios.json` in the
  evidence archive.
- **Comparison with records.** QA compares the run with every observation record in the source that has a generated
  `csweet:observed` section (`BrowserScenarios.Compare`). It lists every failed check and every difference in
  scenarios, expectations, observations, results and event sequence. When no record has a generated section, QA is
  told the measured values were written by hand.
- **Budget.** Declared interaction gets one more behavioral run, for the standard run.
- **Prompt.** For declared criteria, QA starts with `run_scenario_contract` and reports every failed check and record
  difference in one verdict. It uses its own scripts only where the scenario checks do not really measure a criterion.

## Evidence without the 4 MiB cap

(Held back from 5.8.0 on 2026-11-12 until C-Sweet staged evidence parts and SDK 5.24.0 shipped; both are now in.)

- **Runner.** It keeps everything the run recorded (result, authored test, scenario evaluation, screenshot, trace),
  hashes the archive in 1 MiB blocks, and reports `omittedEvidence: []` for compatibility.
- **Checks.** Receipt, report and transfer checks accept any positive length, including the smoke-test report.
- **Requirements.** This needs a C-Sweet Core and compute provider that stage evidence in parts (`ComputeEvidenceParts`).
  An older Core still carries archives up to 4 MiB inline.
